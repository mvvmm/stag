# 1.6.1 cf CLI: Implementation Plan

> Status: **in progress (2026-09-29).** Parent: [implementation-plan.md](../implementation-plan.md) step 1.6.1. Replaces the Wrangler setup from [0.5](0.5-repo-and-cloudflare-deploy.md).

## Goal

Move the deploy tooling from Wrangler to Cloudflare's new `cf` CLI ([launch post](https://blog.cloudflare.com/cloudflare-cf-cli-launch/), open beta). Wrangler gets a final major version that points to `cf` when the beta ends, then 18 months of maintenance, so we switch while the setup is still tiny (an assets-only Worker, no script, no bindings).

When it's done:

- `cloudflare.config.ts` is the only Cloudflare config. `wrangler.jsonc` is gone.
- Vite builds the Worker through `@cloudflare/vite-plugin` (cf's default path). Static assets come from the Vite build.
- `pnpm dev` / `pnpm build` go through `cf dev` / `cf build`. The `cf:*` scripts use `cf deploy` / `cf previews deploy`.
- Workers Builds deploys production and Previews with `cf`, and the PR still gets its Preview comment and the `Workers Builds: stag` check.
- Nothing in our scripts, config or docs calls `wrangler`.

**Full dogfooding.** The user works at Cloudflare and wants us on `cf` everywhere, at least to start. No Wrangler fallbacks. Anything cf can't do yet, or does badly, goes into a friction log (below) to report upstream, not a quiet workaround. Agents use `cf` (not the dashboard or raw API calls) for any Cloudflare operation it covers: Builds settings, previews, tokens, logs.

Out of scope: Worker code, bindings, R2/D1, a custom domain.

## What we found (research, 2026-09-29)

- `cf` is `1.0.0-beta.5` on npm (unscoped `cf`, bins `cf`/`cloudflare`, Node ≥ 22). The `developers.cloudflare.com/cf/…` docs are not live yet (404; [docs PR](https://github.com/cloudflare/cloudflare-docs/pull/33735)). The CLI's own help and `cf cli search` are the reference for now.
- Auth: `CLOUDFLARE_API_TOKEN` first, then OAuth profiles (`cf auth …`). The per-Worker scoped token from 0.5 should keep working (same API).
- `cf migrate`, run on a scratch clone:
  - `--bundler wrangler` (the default without the Vite plugin) writes `cloudflare.config.ts` **and** `wrangler.config.ts` (`assetsDirectory: "./dist"`), and cf hands the build/deploy to Wrangler. Rejected.
  - `--bundler vite` writes only `cloudflare.config.ts` (name, compatibility date and observability carried over as `headSamplingRate` etc.), but **not** `assets.directory`: "Configure static assets in the Vite project". Previews become an `if (ctx.isPreview)` branch, a duplicate of the main one here. The file starts with a `throw` until the TODOs are resolved.
- Previews: `cf previews deploy [name]` (the name defaults to the CI/Git branch), `--prebuilt` to reuse the build output. Production: `cf deploy [--prebuilt]`.
- **Wrangler stays in the lockfile.** `@cloudflare/vite-plugin@1.62` depends on `wrangler@4.143` (dependency + peer) and uses it internally. We never call it and drop it from our `devDependencies`. It's gone for good once the plugin stops depending on it.

## Decisions

| Area | Decision | Notes |
|---|---|---|
| Migration path | **Vite plugin** (`cf migrate --bundler vite`) | cf's intended path: one config file, and Vite owns the build. Wrangler only remains as the plugin's internal dependency. |
| Workers Builds | **Switch to cf, verify on the 1.6.1 PR** | The PR is the test. No Wrangler fallback: if the Preview comment or the `Workers Builds: stag` check breaks, it goes in the friction log and to the cf team, and the PR waits (or we decide together how to unblock). |
| Dogfooding | **cf for everything, friction log** | The user is a Cloudflare employee. Every rough edge (missing docs, `cf migrate` TODOs, Builds gaps, agent UX such as the `--help` discovery banner) gets a line in the friction log with repro and version. |
| Dev entry point | **`pnpm dev` = `cf dev`** | All-in on cf's front door: `cf dev` / `cf build` start Vite underneath. Port 5746, COOP/COEP and the replay-fixture middleware must keep working (acceptance). |

### Defaults I picked (object if you disagree)

- **Pin `cf` exactly** (no `^`) as a devDependency, so Builds runs the same version as local, **and bump it to the latest beta at the start of every step** (dogfooding means staying current; a bump that breaks something goes in the friction log).
- **No `ctx.isPreview` branch.** Previews are identical to production (0.5 decision), so one config object, no duplicate.
- **Scripts:** `dev` → `cf dev`, `build` → `tsc --noEmit && cf build`, `preview` → `vite build && vite preview` (cf can't serve its build locally, see the friction log), `cf:dev` removed. `cf:deploy` → `pnpm build && cf deploy --prebuilt`, `cf:preview` → `pnpm typecheck && cf previews deploy` (builds as a Preview itself; `--prebuilt` refuses a normal `cf build`).
- **Workers Builds commands** (set with `cf builds workers update` under the user's `cf auth login`): production build `pnpm build`, deploy `pnpm exec cf deploy --prebuilt`. Previews: build `pnpm typecheck`, deploy `pnpm exec cf previews deploy`, which does the one Preview-stamped build itself (see the friction log). Patched onto existing Previews too (`--patch-existing-previews true`).
- **Vitest keeps its Node environment.** The plugin is left out of `vite.config.ts` when `process.env.VITEST` is set (it clashed with Vitest's server), which is smaller than a separate `vitest.config.ts`.
- **Gitignore** whatever cf generates: `.cloudflare/` (types, build output) and cf's local state, if it lands in the repo.
- **Telemetry:** check what `cf` collects ([telemetry.md](https://github.com/cloudflare/cf/blob/main/packages/cli/telemetry.md)) and turn it off in scripts/CI if there's a switch. Mention it to the user either way.

## Steps

1. **Branch** `1.6.1-cf-cli` off `main` (after 1.6 merges).
2. **Migrate.** `pnpm add -D -E cf @cloudflare/vite-plugin`, `cf migrate --bundler vite`, then resolve the TODOs by hand: drop the `isPreview` branch and the `throw`, add `cloudflare()` to `vite.config.ts` as an assets-only Worker (no entry), delete `wrangler.jsonc`, `pnpm remove wrangler`. Update `pnpm-workspace.yaml` `allowBuilds` for whatever still needs a postinstall (workerd, esbuild; check cf's deps).
3. **Scripts + gitignore** as in the defaults. `.env.example`: say that cf (not Wrangler) reads it, and check that cf actually loads `.env`. If it doesn't, load it in the scripts (`node --env-file`) or document exporting it.
4. **Local checks.**
   - `pnpm dev`: the game runs on :5746, `crossOriginIsolated === true`, the replay fixtures list/save/load in the pane, HMR works.
   - `pnpm build`: `dist/` (or wherever the plugin now writes, fix any paths that assume `dist/`) has `_headers`, `robots.txt`, hashed `/assets`.
   - `pnpm preview` / `cf:dev`: `curl -I` shows COOP/COEP, `noindex`, immutable `/assets/*`.
   - `pnpm check` is green (Vitest unaffected).
5. **Scoped token.** `pnpm cf:preview` with the `.env` token deploys a Preview. Deploying another Worker name is still refused.
6. **Workers Builds.** Switch the deploy and preview commands to cf with `cf builds …` (👤 `cf auth login` if the scoped token can't). Push the branch.
7. **Verify on the PR.** Cloudflare comments the Preview URL, `Workers Builds: stag` goes green, and on the Preview (agent-browser): WebGPU renders, `crossOriginIsolated`, headers, `?debug` with the build commit, and the stable URL follows a second push.
8. **Docs.** AGENTS.md (commands table, Repo & deploy, credentials: `wrangler` → `cf`, config file name, and a rule: Cloudflare operations go through `cf`, rough edges go in the friction log), the Hosting row in `implementation-plan.md`, a note in the 0.5 plan that 1.6.1 replaced Wrangler, README if it mentions Wrangler. Implementation notes here. Tick 1.6.1.
9. **Friction log → upstream.** Turn the log into issues/feedback for the cf team (the user decides where: GitHub issues on `cloudflare/cf` or internal).
10. **Devlog** `devlog/1.6.1-cf-cli/`: short entry (why we switched while it's small, what `cf migrate` did and didn't do, the Wrangler-in-the-lockfile catch, the friction log highlights). Screenshots: the PR's Preview comment + checks, the terminal output of `cf previews deploy`.
11. **Push, green, report the Preview URL.** The user merges, then confirm production deployed through cf (the Builds log shows `cf deploy`).

## Implementation notes

- `cloudflare.config.ts`: name, compatibility date, observability. No entrypoint = assets-only. Added to `tsconfig.json`'s `include` so the typecheck covers it.
- `vite.config.ts`: `cloudflare({ experimental: { newConfig: true, headersAndRedirectsDevModeSupport: true } })`, so `pnpm dev` serves `_headers` like production. The explicit COOP/COEP in `server.headers` stays (belt and braces).
- `cf build` writes to `.cloudflare/output/v0/workers/default/assets/` (gitignored with `.cloudflare/`). The built bundle is byte-identical to the Wrangler-era `vite build` (same `index-BGIT_-Zd.js` hash).
- Verified locally: `pnpm check` (298 tests), `cf dev` on :5746 with `crossOriginIsolated`, the replay endpoints and the game rendering, `pnpm preview` headers, and `pnpm cf:preview` → https://1-6-1-cf-cli-stag.root-mvm.workers.dev with COOP/COEP, `noindex`, immutable `/assets/*` and `robots.txt`.

## Friction log

For the cf team. Version, repro, what we expected.

- `cf@1.0.0-beta.5`: `developers.cloudflare.com/cf/…` docs 404; only `--help` and `cf cli search` to go on.
- `cf migrate` (no Vite plugin declared) defaults to `--bundler wrangler` and writes a `wrangler.config.ts`, so a simple assets-only Worker doesn't leave Wrangler without knowing `--bundler vite`.
- `cf migrate --bundler vite` drops `assets.directory` ("Configure static assets in the Vite project") instead of wiring the assets-only case into the plugin config.
- `cf migrate` turns an empty `"previews": {}` into a full duplicate `ctx.isPreview` branch plus a required TODO.
- `@cloudflare/vite-plugin` depends on `wrangler`, so "migrated to cf" still installs Wrangler.
- `cf cli search "create a preview deployment for a branch"` doesn't return `cf previews deploy` (top hits: custom-pages preview tokens, waiting rooms, Pages deployments).
- Every `--help` prints the "STOP: AGENT COMMAND DISCOVERY" banner, even for a single, targeted command's help.
- `NO_COLOR=1` is overridden by a `FORCE_COLOR` cf sets, so Node prints a warning with a stack trace on every command.
- `cf build` has no way to make a Preview build. Only `cf previews deploy` stamps its build `isPreview: true` (internally through `CLOUDFLARE_PREVIEW_BUILD=true`). A plain `cf build` gets `false`, and `cf previews deploy --prebuilt` then refuses it ("Build Output was not created by a Preview build"). Checked in cf's source: no flag or `--mode` exposes it. Workaround inside cf: the Previews' Builds build command is only `pnpm typecheck`, and `cf previews deploy` builds. A `cf build --preview` would let CI build once and deploy either way.
- No cf command serves a production build locally (the `wrangler dev` on built assets we had as `cf:dev`). `cf dev` has no `--prebuilt`. `vite preview` with the plugin fails on `cf build` output (`ENOENT .wrangler/deploy/config.json`), so `pnpm preview` runs a separate plain `vite build` to `dist/`.
- The Vite plugin fights Vitest when both share `vite.config.ts` ("There is already a server associated with the config"). We leave the plugin out when `process.env.VITEST` is set.
- The cf config lives behind `experimental.newConfig` on the Vite plugin (`cf dev`/`cf build` force it on, but plain `vite` needs the flag). And `_headers` in dev also needs `experimental.headersAndRedirectsDevModeSupport`.
- (By design, as far as we can tell.) `cloudflare.config.ts` has no assets directory (`assets` takes only handling options): the build tool owns the output. So the Cloudflare setup is cloudflare.config.ts **plus** the plugin in vite.config.ts. Worth one line in the docs.
- (Expected RBAC, not a bug.) The per-Worker scoped token (Workers → Specified Workers → stag, Editor) gets a 403 on `cf builds workers get` for its own Worker. The user's `cf auth login` handles Builds settings. Gotcha: cf loads `CLOUDFLARE_API_TOKEN` from the project's `.env`, which takes precedence over the login, so account-level commands have to run outside the repo (or the token would need `--profile` to win, which it doesn't).
- (Minor.) `cf cli search` is phrasing-sensitive: "find the id of a worker by name" misses `cf workers scripts search`, and "look up a worker script id" finds it. That's the command that gives the script tag `cf builds workers …` needs.
- `pnpm add cf` on pnpm 12 hits the `minimumReleaseAgeExclude` policy (the beta, `@cloudflare/vite-plugin` and `@cloudflare/codemods` were published within the window), so cf's release cadence forces an exclusion list. The install then pulled in `wrangler@4.143.0` as the plugin's peer without flagging it, and only CI's `--frozen-lockfile` policy check caught it (every job failed on the first push), so Wrangler needed an exclusion too.
- Nice: `cf previews deploy` prints clean JSON with the stable and per-deployment URLs, and cf loads `.env` by itself (no wrapper needed).

## Acceptance criteria

- [ ] `cloudflare.config.ts` is the only Cloudflare config file, with no TODOs or `throw` left. `wrangler.jsonc` is deleted.
- [ ] `wrangler` is not in `package.json`, and `grep -ri wrangler` over the tree (excluding the lockfile, the 0.5 plan and devlog history) finds nothing.
- [ ] `pnpm dev` (via `cf dev`) serves on :5746 with cross-origin isolation, and the replay-fixture endpoints work.
- [ ] `pnpm check` and all four CI jobs pass.
- [ ] `pnpm cf:preview` deploys a Preview with the scoped `.env` token, and `pnpm cf:deploy` is wired the same way (not run, since production deploys come from merges).
- [ ] Workers Builds builds the PR with cf: the Preview URL is commented, `Workers Builds: stag` is green, and the Preview matches production (WebGPU, COOP/COEP, `noindex`, immutable assets, `?debug` build tag).
- [ ] After the merge, production is deployed by `cf deploy`.
- [ ] No Wrangler fallback anywhere (scripts, Builds, docs). Every gap is in the friction log.
- [ ] The friction log is handed to the cf team.
- [ ] AGENTS.md, the implementation plan and this plan are updated, and the devlog entry is in the PR.
