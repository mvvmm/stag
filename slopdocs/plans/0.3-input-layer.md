# 0.3 Input Layer: Implementation Plan

> Status: **done (2026-09-27).** Parent: [implementation-plan.md](../implementation-plan.md) step 0.3.

## Goal

Build the real input layer:

- keyboard and mouse state from the DOM
- **action mapping** through data-driven binding presets
- the **mouse-to-ground aim point**
- a per-tick **`InputFrame`** handed to the pure simulation

It supports **two control schemes** side by side (MMO-style WASD and League-style right-click-to-move). Step 1.2 prototypes movement with both, and the 1.7 feel gate picks one (or keeps both as a setting).

When it's done, `pnpm dev` shows an **input test scene**: an aim marker under the cursor, a throwaway "pawn" box you can move with either scheme, a move-to target pin, and an overlay showing the live `InputFrame`. `pnpm check` must pass.

Out of scope, handled by later steps:

- the real player controller: acceleration, facing, collision (1.2, 1.3)
- camera follow (1.4)
- ability casting, cooldowns and input buffering (2.1)
- the final keybinds and the dodge decision (2.2)
- enemy-under-cursor targeting for right-click attacks (2.5 / 3.x)
- rebinding UI (16.1)
- gamepad support

## Decisions

| Area | Decision | Notes |
|---|---|---|
| Sim boundary | **Per-tick `InputFrame` snapshot** | The shell samples input before each tick and calls `simulation.step(dt, frame)`. Systems become `(world, dt, rng, input) => void`. The sim stays pure and testable, which also sets up input recording/replay later. |
| Edge latching | **Latched presses and releases** | A press (or release) is reported to exactly one tick: the first tick sampled after it happened. When a frame runs 0 ticks, it waits for the next one. When a frame runs several, only the first sees it. A tap that goes down and up within one frame shows up as `pressed` + `released` with `held` false. |
| Control schemes | **Both, decided at 1.7** | Two presets, `mmo` and `moba`. The `InputFrame` carries both a WASD move vector and a right-click move command. The sim decides what to do with them. |
| Action set | **Provisional full set, named by role** | `primary`, `ability1`–`ability3`, `ultimate`, `dodge`, `interact`, `stop`, `pause`. Final binds come in 2.2; only the tables change. Dodge is in provisionally (universal vs form-specific is still open for 2.2). |
| Opposite keys | **Last pressed wins** | A held, then D pressed → right; release D → left again. Per axis. Better for micro-adjustments than cancelling out. |
| RMB movement (moba) | **League-style click + hold** | RMB down sets the move target. While held, the target follows the cursor every tick. After release, the target stays until you arrive or press `stop` (S). |
| Demo | **Input test scene** (throwaway) | Keeps the orbiting boxes and adds an aim ring, a pawn box, a target pin and an input overlay. 1.1/1.2 replace it. |

### Presets

| Action | `mmo` (default) | `moba` |
|---|---|---|
| move | WASD / arrow keys (vector) | RMB (move-to point) |
| primary | RMB | RMB (the sim later decides: enemy under cursor → attack, otherwise move) |
| ability1 / 2 / 3 | 1 / 2 / 3 | Q / W / E |
| ultimate | 4 | R |
| dodge | Space | Space |
| interact | LMB | LMB |
| stop | – | S |
| pause | Esc | Esc |
| aim | cursor on ground | cursor on ground |

Debug bindings (shared by both presets; revisited in 0.4): `I` interpolation, `T` time scale, `B` switch preset. `P` goes away because `pause` (Esc) replaces it.

### Defaults I picked (object if you disagree)

- **Physical keys.** Bindings use `KeyboardEvent.code` (`KeyW`, `Digit1`), so AZERTY and other layouts get the same physical layout. Mouse buttons are `Mouse0` (left) and `Mouse2` (right). The middle button and wheel aren't bound yet.
- **Bindings are data.** Presets live in `input/bindings.ts` as `Record<Action, Binding[]>` plus a move spec (`keys` with up/down/left/right lists, or `pointer` with the button). Rebinding (16.1) just edits this data.
- **Ground-plane coordinates.** The sim works in `{ x, z }` on the ground plane (`Vec2` in `core/math.ts`). The move vector is **camera-relative**: raw screen-space input (right, up) is rotated by the camera's yaw into world x/z, then normalized to length ≤ 1 (diagonals aren't faster). The shell does this rotation with a pure helper, so the sim only sees world directions.
- **Move command, not destination state.** The input layer stays stateless about where you're going. In `moba`, `InputFrame.moveCommand` holds the cursor's ground point on every tick where RMB went down or is held, and `null` otherwise. The sim stores the persistent target on the entity and clears it when you arrive or press `stop`.
- **Aim point.** Each frame, `render/aim.ts` casts a ray from the camera through the last known pointer position onto the plane `y = 0` (`GROUND_Y` constant), using Babylon's `createPickingRay`, which accounts for our hardware scaling. The result goes into the input state, and each tick samples the latest value.
  - It's recomputed every frame even if the mouse is still, because the camera will move (1.4).
  - If the ray misses the plane, or the pointer has never been over the canvas, the previous aim is kept (initially `{ 0, 0 }`).
  - The aim can be up to one frame stale by the time a tick sees it; that's acceptable.
- **Two consumers, two latches.** The sim samples per tick (`sampleTick()`). The shell samples per frame (`sampleFrame()`) for shell-level actions (`pause`, debug toggles) that must still work while the loop is paused. Each has its own latched edges, so one never steals the other's presses.
- **Browser hygiene:**
  - Key events are listened to on `window`, pointer events on the canvas, and `pointermove` on `window` (so aim keeps tracking past the canvas edge).
  - The context menu is suppressed on the canvas (RMB is a game button).
  - `preventDefault` runs on bound keys (so Space doesn't scroll), but never when Cmd/Ctrl/Alt is held, so browser shortcuts keep working.
  - Key repeat is ignored.
  - On window `blur` or tab hidden, every held key and button is released (with `released` edges), so nothing gets stuck.
  - No pointer lock: the cursor is the aim.
- **Preset persistence.** The active preset is remembered in `localStorage` (wrapped in try/catch, falling back to `mmo`). Switching presets clears held state.
- **Pure where possible.** Everything except `input/dom.ts` and `render/aim.ts` is DOM- and Babylon-free and unit-tested. `input/` joins `core/`, `ecs/` and `systems/` under the "no Babylon/Preact" rule, with `dom.ts` as the one DOM adapter.

## `InputFrame`

```ts
type Action =
  | "primary" | "ability1" | "ability2" | "ability3" | "ultimate"
  | "dodge" | "interact" | "stop" | "pause";

type InputFrame = {
  /** World ground-plane direction, length ≤ 1. Zero when idle or in the moba scheme. */
  move: Vec2;
  /** moba: cursor ground point while RMB went down / is held this tick; otherwise null. */
  moveCommand: Vec2 | null;
  /** Cursor on the ground plane. */
  aim: Vec2;
  held: ReadonlySet<Action>;
  /** Went down since the previous tick (reported to exactly one tick). */
  pressed: ReadonlySet<Action>;
  /** Went up since the previous tick (reported to exactly one tick). */
  released: ReadonlySet<Action>;
};
```

## Architecture

```
input/
  actions.ts     Action union, InputFrame type, emptyInputFrame()      (pure)
  bindings.ts    Preset type, mmo + moba + debug presets               (pure data)
  state.ts       createInputState(preset): raw events in → sampleTick()/sampleFrame() out,
                 latching, last-pressed-wins axes, move command, release-all  (pure, tested)
  dom.ts         attaches DOM listeners to an InputState; preventDefault, blur, contextmenu
render/aim.ts    pointer (CSS px) → picking ray → ground point, written to InputState each frame
core/math.ts     + Vec2, rotateByYaw(), normalizeClamp()
```

Frame flow (inside `engine.runRenderLoop`):

```
aim.update()                         // ray → ground, input.setAim(point)
shellFrame = input.sampleFrame()     // pause / debug toggles, even while paused
loop.advance(frameSeconds)           // per tick: sim.step(TICK_DT, input.sampleTick(cameraYaw))
fitCanvas; meshSync.sync(alpha); scene.render()
```

The loop's `update` becomes a closure: `(dt) => simulation.step(dt, input.sampleTick(cameraYaw))`. `core/loop.ts` itself doesn't change.

## Implementation notes

- **Verified in headless Chrome** (production build, real WebGPU adapter, driven over CDP with synthetic keyboard and mouse input), at both 1× and 2× device scale factor:
  - Aim: the canvas center projects to exactly (0, 0), the camera target. Off-center points give the same ground coordinates at 1× and 2×. In screenshots the ring sits under the cursor.
  - mmo: W → (0, 1); W+D → (0.71, 0.71); D held then A → x = −1, releasing A → x = 1.
  - Taps 40 ms apart: 10 Space → `dodge` 10, 5 × `1` → `ability1` 5. At ×0.05, 6 taps 400 ms apart → 6 more.
  - Esc pauses (0 ticks/s) and unpauses while paused. A synthetic window blur releases a held `2`.
  - The context menu and Space default are prevented. Cmd+R isn't.
  - moba: a right-click sets `moveCommand` and `primary`, holding and dragging steers the target, S stops. LMB held then RMB (a chord) registers both. Q/W/E/R → ability1–3 + ultimate.
  - `B` switches presets, and the choice survives a reload.
- **Mouse buttons come from pointer events, not mouse events.** The first version listened to `mousedown`/`mouseup`, and right-click did nothing. Babylon's scene input handling calls `preventDefault()` on `pointerdown`, which (per the Pointer Events spec) suppresses the compatibility mouse events. `input/dom.ts` now listens to `pointerdown`/`pointermove`/`pointerup`/`pointercancel` and diffs the `buttons` bitmask on each one. That way a second button pressed during a chord, which only fires `pointermove`, still registers. New presses only count when the target is the canvas (not UI panels); releases count anywhere.
- **Repeated presses within one tick collapse.** `pressed` is a set, so tapping the same key several times between two ticks reaches the sim as one press. At ×1 a tick is 16 ms, so humans can't hit this. At ×0.05 it takes taps less than ~330 ms apart. The per-frame debug keys behave the same way within one frame. If abilities ever need counted presses, the latch can become a counter.
- **Cmd on macOS:** keys pressed while Cmd is held never get a `keyup`, so keydowns with Cmd/Ctrl/Alt are ignored. Pressing Cmd itself releases everything.
- **Babylon's `createPickingRay` takes CSS pixels** and applies the hardware scaling level itself (checked in `ray.core.js`), so `render/aim.ts` passes pointer coordinates straight through.
- **Order within a frame:** fit the canvas → project the aim → compute the camera yaw → `sampleFrame()` (pause, preset switch, demo debug keys) → `loop.advance` (one `sampleTick` per tick) → render. The preset switch lives in the shell (it's input infrastructure). `I` and `T` live in the demo.
- **Demo additions:** the pawn is tinted orange through a new `meshOf(entity)` accessor on the mesh sync, exposed on `Shell`. The overlay shows how many ticks saw each action pressed, which makes lost or doubled presses easy to spot.
- **Your dev server was already on 5746**, so the automated run used `pnpm preview --port 5747`.
- **Not yet verified by hand:** how movement feels, real tab switching and window blur with held keys, Safari and Firefox.
