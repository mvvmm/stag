# 0.4 Dev Tooling: Implementation Plan

> Status: **done (2026-09-27).** Parent: [implementation-plan.md](../implementation-plan.md) step 0.4.

## Goal

Build the dev tooling every later step leans on:

- a **debug pane** (Tweakpane) that controls every dev tool, always there in debug builds (<kbd>`</kbd> hides/shows it), with a **tunables registry**: live-tweak values, keep the tweaks across reloads, copy them back into code
- an extended **stats overlay** with a frame-time graph and a **per-system profiler**
- **debug draw**: immediate-mode shapes callable from anywhere, systems included
- the **Babylon Inspector**, lazy-loaded
- a **command registry** (pane buttons + `__game.run`) and a `window.__game` handle for the console and agent-browser
- **wireframe** and a **free debug camera**

We decided to spend real time here: tooling that exists before we need it saves time in every later step. The work is split into three sub-steps, each with its own plan, commit and devlog entry:

| Step | Scope |
|---|---|
| **0.4** (this plan) | Everything listed above |
| **0.4.1 Scenes & reset** | Scene registry + switcher, in-place teardown/reset, seed display + restart, frame step, entity picker |
| **0.4.2 Record & replay** | Auto-recording of the session, state checksums, save/load replay files, playback |

The decisions already made for 0.4.1 and 0.4.2 are recorded [at the end](#decided-for-041-and-042) so their plans start from them.

When 0.4 is done, `pnpm dev` shows the input test scene with the debug pane docked top right, and every tool above is a control in it. The keyboard stays the game's. `pnpm check` must pass.

> **Revised after the first review** (same day): the first version had a dev-keys mode. See [Revision](#revision-pane-only-no-dev-keys). The plan below describes the final state.

Out of scope:

- everything in 0.4.1 and 0.4.2
- cheats (god mode, spawn enemy, give augment): later steps add them as one-line commands
- a settings menu for players (16.1)

## Decisions

| Area | Decision | Notes |
|---|---|---|
| Availability | **Always in `pnpm dev`; `?debug` in production** | `DEBUG = import.meta.env.DEV \|\| ?debug`. The heavy parts (Tweakpane, the Inspector) are dynamic imports, so normal players never download them. Without the flag, <kbd>`</kbd> does nothing, stored tweaks are ignored and debug draw is a no-op. That lets us debug PR previews (0.5) and playtest builds without redeploying. |
| Controls | **Pane only; no dev keybinds** | The keyboard always carries the live game bindings. Every dev tool is a control in the debug pane. The pane is always there in debug builds and can be collapsed; <kbd>`</kbd> (handled by the dev tools, not a game binding) is the only way to hide/show it. |
| Tuning UI | **Tweakpane 4** (+ `@tweakpane/core` for its types) | Small, framework-free, and has sliders, folders, lists and buttons. Loaded lazily. It's a debug view, so it may read and write tunables and debug state directly; the "UI reads signals" rule is for game UI. |
| Tunables | **Pure registry, `defineTunables`** | `core/tuning.ts` has no DOM and no Babylon, so systems can import it. It returns a plain object the code reads live, so nothing gets cached. The pane builds its folders from the registry. |
| Tweaks → code | **Saved tweaks + "copy changes"** | Tweaks persist in localStorage and survive reloads/HMR. Changed values are marked in the pane, with reset per value, per group and for all of them. "Copy changes" puts a snippet on the clipboard (`pawn.speed: 6 → 7.5`), and you (or I) edit the default in code. Code stays the source of truth. |
| Stats | **Extend our Preact overlay** | Modes off / compact / full, picked in the pane. Full adds a frame-time graph, CPU/GPU frame time, draw calls, meshes, entities, heap and the profiler. Published at ~4 Hz through signals, as today. |
| Debug draw | **Immediate mode, callable from the sim** | `core/debugDraw.ts` is a pure, write-only buffer. It's a no-op when disabled and never feeds back into the simulation, so determinism and tests are unaffected. Render drains it each frame. Shapes have categories that toggle in the pane. |
| Persistence | **Remember settings, not visibility** | Folder/pane collapse state, stats mode, input overlay, debug-draw on/off + categories, wireframe and tunable tweaks survive reloads. The pane is shown on every load (hiding with <kbd>`</kbd> isn't remembered). The Inspector and the free camera always start off. |
| Input overlay | **Debug-only** | The input test's overlay (actions, move mode, aim) only shows in debug builds, with a pane toggle. |
| Extras | **Profiler, commands + `window.__game`** | In 0.4. Scenes/reset/seed/frame step/entity picker come in 0.4.1, and record & replay in 0.4.2. |

### Pane layout

| Folder | Controls |
|---|---|
| Loop | paused, time scale (slider), interpolate, input preset |
| View | stats (off/compact/full), input overlay, wireframe, free camera, Babylon Inspector button |
| Debug draw | enabled, one toggle per category (they appear as code draws them) |
| Tunables | Copy changes, Reset all, a folder per group (● marks changed values, double-click a label to reset it, "Reset group") |
| Commands | a button per command that asks for one; hidden while there are none (cheats come later) |

The game-side `I`/`T`/`B` debug bindings from 0.3 go away: the game keyboard is now only game actions (<kbd>Esc</kbd> still pauses, as a game action).

### Defaults I picked (object if you disagree)

- **Commands** live in `debug/commands.ts`: `define({ id, label, group, button?, run })`. `window.__game.run(id)` runs any of them. The pane shows a button for each command unless it sets `button: false` (the built-ins do, because they mirror pane controls). Later steps add cheats by writing one `define` each.
- **The input layer knows nothing about the dev tools**, except that `InputState.setMouseButtons(false)` stops feeding mouse buttons to the game while the free camera uses the mouse (held buttons are released with edges; keys keep working).
- *(First version, removed:)* `InputState` had `setDevMode(on)`:
  - on: releases all held game actions (reported as `released` on the next tick). From then on, game controls are ignored, and `sampleTick` sees no actions, `move` = 0 and `moveCommand` = null.
  - `sampleFrame()` gains `devPressed: ReadonlySet<Control>` (the raw codes pressed this frame while in dev mode). The shell maps them to commands.
  - <kbd>`</kbd> (`Backquote`) is reported as a frame-level toggle in both modes, but only when `DEBUG` is on.
  - `DebugAction` and `DEBUG_BINDINGS` are removed.
- **Keys typed into the pane or the Inspector never reach the game (or toggle the pane).** `input/dom.ts` ignores key events whose target is an `input`, `textarea`, `select` or content-editable element. Pointer presses already only count on the canvas.
- **Tunable kinds:** `number` (`min`, `max`, `step`), `boolean`, and `select` (a list of strings). The value types are inferred, so `PAWN.speed` is a `number`. Defining a group again replaces it (module reloads) and carries over tweaks that are still valid. Interactive sets clamp numbers to the range.
- **Tweaks are applied at startup, before the first tick** (only when `DEBUG` is on). Stored values that no longer match a tunable (renamed, removed, wrong type, out of range) are dropped silently. Changing a sim tunable mid-run is a sim input. 0.4.2 records those changes as replay events.
- **First tunables:** the demo pawn speed (moved off the `Pawn` component), an orbit speed scale, and the camera (`pitch`, `distance`, `fov`). The time-scale steps stayed a constant because tunables have no list type; the pane has a time-scale slider instead. Real game values join as they appear (1.2 movement will be the first big user).
- **The frame-time graph and profiler stay low-frequency.** The shell collects every frame into ~250 ms buckets (avg and **max** frame time, so hitches show up) and publishes the last 60 buckets (15 s) at 4 Hz. The graph is a small SVG in the stats overlay.
- **The profiler is timed from outside the simulation.** The simulation's systems become named (`{ name, run }`) so minified `?debug` builds still show readable names. The shell wraps each system with a `performance.now()` timer, so the sim still never reads the clock. It also times the render phases (mesh sync, debug draw, `scene.render()` CPU time). Full stats show avg/max ms per system and phase over the last second, sorted by cost.
- **GPU frame time** comes from WebGPU timestamp queries on the main pass (`engine.enableGPUTimingMeasurements`). Debug builds request the `timestamp-query` feature, and it reads "n/a" when the adapter lacks it. Draw calls come from `SceneInstrumentation`. The JS heap is Chrome-only (`performance.memory`). The instrumentation only runs while full stats are shown.
- **Debug draw details:**
  - Shapes: `line`, `arrow`, `circle` (flat on the ground), `box`, `point`, `path` (polyline) and `text`.
  - Colors: a small named palette (`red`, `green`, `blue`, `yellow`, `cyan`, `magenta`, `white`) or an RGB value.
  - Every call takes a `category` (`general` by default) and an optional `duration` in seconds of game time.
  - Without a duration, a shape drawn during a tick lasts until the next tick (so it stays visible while paused), and one drawn from render code lasts one frame.
  - Duration shapes age with sim time, so slow-mo and pause freeze them too.
  - Lines render as one `LineSystem` in a rendering group on top of the scene (no depth test), updated in place and regrown when it overflows. Text renders as a pool of absolutely positioned HTML labels, projected each frame by `debug/` code (not Preact).
  - Built-in categories: `general`, `grid` (a depth-tested ground grid mesh plus the world axes at the origin), plus whatever systems use. The demo pawn draws its facing arrow and a line to its move target (category `pawn`) as the first real user.
- **Inspector:** `@babylonjs/inspector`, pinned to the same version as `@babylonjs/core` (9.28.0) and loaded with a dynamic import on first open, **only in `pnpm dev` builds** (see the notes). It isn't persisted: it's heavy and it's always an explicit choice. While it's open, the pane and the stats step aside, because it docks panels on both sides of the page.
- **Free camera:** an `ArcRotateCamera` that starts at the game camera's pose and is controlled with the mouse: drag to orbit, right-drag to pan, wheel to zoom. While it's on, mouse buttons don't reach the game (so orbiting doesn't fire `interact` or moba move commands), but the keyboard does. The aim point is projected through the camera that's rendering, so it stays under the cursor while you orbit. WASD stays relative to the **game** camera, so movement directions don't change. (The first version projected aim through the game camera too, which put the aim ring somewhere unrelated to the cursor.)
- **Wireframe** is `scene.forceWireframe`.
- **Overlays:** the pane docks top right. LoopStats becomes the stats overlay (top left), and InputStats moves to the bottom left as a debug-only overlay. Both read a `debugState` signal and step aside while the Inspector is open.
- **`window.__game`** (only when `DEBUG` is on) exposes `world`, `loop`, `rng`, `scene`, `input`, `tunables` (get/set/reset/diff), `debugDraw`, `commands` and `run(id)`. It's typed in `env.d.ts`, so console use and agent-browser `eval` get autocompletion and type checking in scripts. This is also how the automated checks in this and later steps drive the game.
- **Persistence** uses one versioned localStorage key, `stag.debug` (`{ v: 1, … }`), wrapped in try/catch. Garbage or an unknown version falls back to defaults. The input preset keeps its own key from 0.3.

## Architecture

```
core/
  tuning.ts        defineTunables, registry, apply/diff/reset, formatChanges()        (pure, tested)
  debugDraw.ts     shape buffer: tick/frame/duration layers, categories, enabled flag (pure, tested)
input/
  state.ts         + setMouseButtons() (free camera)                                    (pure, tested)
  dom.ts           + ignore keys typed into editable elements
systems/
  simulation.ts    named systems ({ name, run }); optional per-system wrapper hook
debug/
  enabled.ts       DEBUG flag (dev || ?debug)
  persist.ts       versioned stag.debug load/save (parse is pure + tested)
  commands.ts      defineCommand registry, key map                                   (pure, tested)
  frameStats.ts    250 ms buckets, per-phase/system avg/max                           (pure, tested)
  devtools.ts      entry: wires everything to the shell when DEBUG, registers the built-in commands,
                   window.__game; lazy-loads the pane and the Inspector
  pane.ts          Tweakpane: tunables folders, debug-draw categories, loop controls, command buttons (lazy)
  inspector.ts     lazy @babylonjs/inspector show/hide
  debugDrawRender.ts  buffer → LineSystem + HTML labels, grid/axes category
  freeCamera.ts    ArcRotate debug camera, swap in/out
ui/
  Stats.tsx        replaces LoopStats: compact/full, frame-time SVG graph, profiler table
  signals.ts       + debugState, extended stats signal
```

Frame flow (additions in **bold**):

```
fitCanvas; aim.update(game camera); yaw = cameraYaw(game camera)
frame = input.sampleFrame()
shell actions (pause via Esc)
loop.advance(...)             // per tick: **debugDraw.beginTick()**; sim.step (systems **timed**)
meshSync.sync(alpha)          // **timed**
**debugDrawRender.update()**  // **timed**; then debugDraw.endFrame()
scene.render()                // **timed**
**frameStats.push(...)**; publish at 4 Hz
```

## Implementation notes

- **Verified in headless Chrome** (agent-browser, real WebGPU adapter) on the dev server and on the production build with and without `?debug`:
  - First version (dev mode): W moved the pawn in game mode, and holding it while entering dev mode stopped it (released). Esc didn't pause in dev mode, Space did. A right-click in dev mode set no move target. Typing <kbd>G</kbd> into a focused pane number field didn't toggle debug draw.
  - Revision: the pane shows on load, <kbd>`</kbd> hides/shows it, and it's back after a reload even when it was hidden. G no longer does anything, while W still moves the pawn. With the free camera on, holding D moved the pawn while an orbit drag sent no `interact`.
  - Tweaks: `pawn.speed` 7.5 and `camera.fov` 55 persisted, came back with ● markers after a reload, and "copy changes" produced `camera.fov: 46 → 55` / `pawn.speed: 6 → 7.5`. The clipboard write itself is denied in headless Chrome (it works on a real key press or click).
  - Wireframe and the free camera worked; turning the free camera off switched back to the game camera.
  - Inspector (dev) opened and closed, and the canvas went back to the page afterwards.
  - Production without `?debug`: no `__game`, no overlays, no devtools or pane chunk fetched, and <kbd>`</kbd> did nothing. With `?debug`: stored tweaks and settings came back, only the devtools and pane chunks were fetched, and the Inspector button reads "Inspector (pnpm dev only)" (disabled).
- **The Inspector is dev-only.** Even behind a dynamic import, bundling it grew the players' initial JS from 1.52 MB to 1.90 MB gzipped. The Inspector imports Babylon's root barrel, and since our entry does too, Rolldown put every core module the barrel reaches (Havok plugin, particle systems, gizmos, …) into chunks shared with the entry. Guarding the import with `import.meta.env.DEV` removes it from production builds, and the players' initial JS is now +3 KB over 0.3. Deep imports (9.6) should let `?debug` builds have it back.
- **GPU timing:** Babylon's frame-level GPU counter (`EngineInstrumentation.captureGPUFrameTime`) stays at 0 on WebGPU because it needs `encoder.writeTimestamp`, which browsers no longer expose. The main-pass counter uses per-pass `timestampWrites` and works. It only covers the canvas pass, so shadow and post-processing passes will need their own counters later. The device also has to request `timestamp-query` explicitly (Babylon requests no optional features by default).
- **Timer precision:** without cross-origin isolation, Chrome coarsens `performance.now()` to 100 µs, and every system showed 0.00/0.10 ms. The dev and preview servers now send COOP/COEP headers (≈5 µs). Production (0.5) doesn't have them yet; add them there if profiling deployed builds matters.
- **Preact's React alias** (`react` → `preact/compat`) is on by default in `@preact/preset-vite`, and it would have fed the Inspector (Fluent UI, real React 19) our compat layer. We turned it off because we don't use React.
- **Depth-tested grid:** the first version drew the grid through the on-top line buffer, so it drew over the boxes. It's now a static mesh in the normal render group. Everything else stays on top.
- **Shell changes:** `shell.start()` now starts the render loop, so the scene and dev tools (and stored tweaks) are set up before the first tick. The shell also exposes `engine`, `gameCamera`, `addRenderPhase` and `onFrameEnd`.
- Closing the Inspector logs "Keyborg instance … is being disposed incorrectly" from Fluent UI. It's harmless and comes from the Inspector.
- **Checked by hand in Firefox** (your walkthrough video): the pane, stats modes, interpolation and tunable sliders work, and GPU time shows (Firefox exposes timestamp queries).
- **Not yet verified by hand:** the real clipboard, Safari.

## Revision: pane-only, no dev keys

The first version (reviewed the same day) had a **dev-keys mode**: <kbd>`</kbd> switched the keyboard and mouse from the game to debug hotkeys (P pane, S stats, G draw, I Inspector, W wireframe, C free camera, Space pause, T time scale, L interpolation, B preset, H a cheat sheet), with a DEV badge, and no game input while it was on. After trying it, you asked for:

- **no dev keybinds at all:** keys are always the live game bindings, and everything is controlled by clicking in the pane. The cheat sheet and DEV badge are gone.
- **<kbd>`</kbd> only hides/shows the pane.** The pane is always visible in debug builds otherwise (it can still be collapsed).
- **the input overlay is a debug thing,** not part of the game UI.

What changed: `setDevMode`/`devPressed`/`devToggle` left the input layer (it knows nothing about the dev tools again), command keys and `keyLabel` went away, and <kbd>`</kbd> is a small window listener inside `debug/devtools.ts`. The pane gained the input-overlay toggle and an Inspector button (disabled outside `pnpm dev`), and its View and Debug draw folders start expanded. Because the free camera no longer lives inside an input-swallowing mode, it now borrows only the mouse buttons (`InputState.setMouseButtons`).

## Decided for 0.4.1 and 0.4.2

These were decided in the 0.4 interview. Each sub-step still gets its own plan (interview) before code.

**0.4.1 Scenes & reset**

- **In-place reset, no page reload.** Scenes become `{ name, setup(shell) → dispose }`. A reset clears the world, disposes the scene's meshes and listeners, reseeds the RNG, resets the loop's tick count and runs setup again. The engine, pane and Inspector stay open. 3.5 (death & restart) and 6.3 (room transitions) reuse it.
- Scene registry + `?scene=` + a pane dropdown. The input test becomes the first registered scene.
- Seed shown in the pane; restart with the same seed or a new one (pane buttons); `?seed=`.
- Frame step while paused (pane button).
- Entity picker: selecting an entity shows its ECS components live (and editable) in the pane, and the selection is highlighted with debug draw. Open: how picking gets a click without dev keys (e.g. a "pick" toggle in the pane that borrows the mouse like the free camera).

**0.4.2 Record & replay**

- **Always recording** the current session: seed, scene, per-tick `InputFrame`s (delta-compressed) and tunable changes.
- **Checksums:** every N ticks, a hash of the world state is stored. Playback reports "diverged at tick N" instead of drifting silently.
- "Save replay" downloads JSON. "Load replay" (file picker or drag-and-drop) plays it back through the in-place reset. Pause, step and time scale work during playback.
- Later: replays as headless Vitest regression tests.
