# 1.2 Player Movement: Implementation Plan

> Status: **done (2026-09-27).** Parent: [implementation-plan.md](../implementation-plan.md) step 1.2.

## Goal

The real player controller replaces the throwaway demo pawn:

- **Kinematic movement** with snappy linear acceleration and deceleration, velocity that steers toward the new direction, a facing that turns toward the movement direction, and exact stops.
- **Both presets:** WASD steers directly. Right-click-to-move follows a **path around obstacles** (grid A* + smoothing) and brakes to land exactly on the click, with a click marker on the ground.
- **Tuning aids** for this step and the 1.7 feel pass: debug-draw categories, a live speed graph, a motion trail, and movement presets.

When it's done, the arena starts with the player, and moving around with either preset feels responsive and precise. Right-click routes around pillars and walls. WASD still walks through walls until 1.3. `pnpm check` must pass.

Out of scope:

- collision and sliding (1.3). The nav grid and the inflated-shape geometry are built so 1.3 can reuse them.
- camera smoothing, look-ahead and bounds (1.4)
- a real character model and animations (1.6). The player is a grey-box capsule with a nose.
- facing the cursor while casting or attacking (2.x), dodge (2.2), speed modifiers (4.1), per-form movement data (10.1)
- enemy pathing and steering (3.4), which will reuse `nav/` and the locomotion system

## Decisions

| Area | Decision | Notes |
|---|---|---|
| Acceleration | **Linear, Balanced by default** | Constant accel and decel, tuned separately. The plan started with Snappy (full speed in ~0.06 s, stop in ~0.04 s). After playing, you picked **Balanced** as the default: full speed in ~0.12 s, stop in ~0.09 s. Velocity clamps to exactly 0, so stops don't drift. |
| Direction changes | **Velocity steers** | Velocity accelerates toward the desired velocity as a vector. A reversal brakes through zero, and a 90° turn arcs very slightly. A separate `turnAccel` applies when the desired direction points against the current velocity, so reversals can be sharper than starts. This gives forms different handling later. |
| Facing | **Movement direction, with a turn rate** | Like League: the character faces where it moves, rotating at a fast tunable rate (default 540°/s), and keeps its facing when it stops. Facing the cursor while casting comes with abilities (2.x). |
| Pathing | **In 1.2, for click-to-move** | Nav data comes from the obstacle entities, inflated by the player radius. Right-click routes around obstacles now, even though WASD still clips until 1.3. 1.3 collides against the same inflated shapes. |
| Path algorithm | **Grid A* + string pulling** | Inflated obstacles rasterized into a 0.25 m nav grid (120×80 cells for this room), 8-connected A*, then line-of-sight smoothing against the exact inflated shapes, so paths are any-angle and hug corners. Repaths only when the goal cell changes. Enemies can reuse it in 3.4. |
| Arrival | **Brake to land exactly** | Full speed along the path, with no slowdown at corners. On the last leg it starts braking at the right distance (`v² / 2·decel`, ~0.3 m at defaults) and stops on the goal with no overshoot or snap. |
| Parameters | **Tunables now, per-form data at 10.1** | One `player` tunables group, read live. Code reads it only through `movementStats(entity)`, so 10.1 can swap in per-form data and 4.1 can layer speed modifiers without touching the controller. |
| Click marker | **A marker where the path ends** | A small ring that pops and fades on the ground at the goal (the click, or the nearest reachable point if you clicked into a wall). It shows on a new click only, not every tick while the button is held. View-only. |
| Tuning aids | **All four** | Debug-draw categories (`movement`, `path`, `navgrid`), a motion trail (`trail`), a live speed graph in the pane, and movement presets (Instant / Snappy / Balanced / Weighty). |

### Defaults I picked (object if you disagree)

- **Movement tunables** (group `player`):

  | Key | Default | Range | Meaning |
  |---|---|---|---|
  | `speed` | 7 m/s | 0–20 | top speed (the pawn was 6; the room is 30 m wide, so ~4 s to cross) |
  | `accel` | 60 m/s² | 1–1000 | speeding up and steering (0 → 7 m/s in ~0.12 s) |
  | `decel` | 80 m/s² | 1–1000 | braking when there's no input, and for arrival (7 → 0 in ~0.09 s) |
  | `turnAccel` | 90 m/s² | 1–1000 | used when the desired direction points more than 90° away from the velocity |
  | `turnRate` | 540°/s | 90–3600 | how fast the facing rotates toward the movement direction |
  | `radius` | 0.4 m | 0.2–0.8 | footprint for nav inflation (and 1.3 collision). The greybox room's tight gap is 1.25 m, so it closes to pathing above 0.625 |

  These are the Balanced preset (you made it the default after playing). The plan started with Snappy's values: accel 120, decel 175, turnAccel 175, turnRate 720.

  At 1000 m/s² a tick changes velocity by ~16.7 m/s, which is effectively instant. That's what the Instant preset uses.
- **The acceleration rule:** each tick `v` moves toward the desired velocity `d` by at most `rate · dt` (a vector move-toward, so it lands exactly). `rate` is `decel` when `d` is zero, `turnAccel` when `dot(v, d) < 0`, and `accel` otherwise. Position integrates with the new velocity (semi-implicit Euler).
- **Facing:** `rotation.y` turns toward `atan2(v.x, v.z)` by at most `turnRate · dt` along the shortest arc, only while speed > 0.1 m/s. Interpolation already uses `lerpAngle`.
- **ECS**, all plain data:
  - `player: { order: MoveOrder | null; orders: number; click: Vec2 | null }` marks the player and holds its click-to-move state. `MoveOrder = { goal: Vec2; waypoints: Vec2[] }`: the smoothed path, next waypoint first. `orders` counts new clicks, and the view pops the marker when it changes. `click` is last tick's move-command point while the button is held (null otherwise). It tells a new click from holding the button, and a moved cursor from a still one.
  - `mover: { velocity: Vec2; desired: Vec2 }` is generic, so enemies can use the same locomotion in 3.x. `desired` is what a controller asks for this tick (`playerControl` now, enemy AI later).
  - The `pawn` component and `pawnSystem` are deleted.
- **Systems**, in order:
  1. `playerControl` (`systems/playerControl.ts`) turns input into a desired velocity.
     - WASD (`input.move` ≠ 0): desired velocity = `move · speed`. This clears any order.
     - `stop` pressed: clears the order, so the player brakes at `decel`.
     - `moveCommand`: repaths when the goal cell differs from the current order's (hold-to-steer repaths as the cursor moves). If it wasn't held last tick, it bumps `orders`.
     - While following an order: desired velocity points at the next waypoint at full speed. A waypoint is consumed once it's within one tick's travel. On the last leg the speed is capped at `√(2·decel·distance)`. When the goal is within one tick's travel, the player lands on it, velocity is zeroed, and the order is cleared.
  2. `locomotion` (`systems/locomotion.ts`) applies the acceleration rule, integrates the position, turns the facing, and draws the debug categories.

  `mover.desired` is overwritten every tick but stays plain data, so snapshots stay exact.
- **`nav/`** (new, Babylon-free, pure and tested; listed under rule 1):
  - `nav/shapes.ts`: an inflated obstacle is a circle with `r + radius`, or a box treated as a rounded rectangle. It provides `insidePadded`, `pushOut`, `segmentDistance` and `segmentClear`, all exact geometry (segment-to-circle and segment-to-box distance). 1.3 builds collision on these.
  - `nav/grid.ts`: `buildNavGrid(room, shapes, pad, cell = 0.25)`, and `navGridOf(world, pad)` for the cached one. A cell is blocked if its center is inside any inflated shape or outside the room's inner bounds. The grid is **derived, not sim state**. It's cached per world and radius (a `WeakMap<World, …>`, rebuilt when the radius tunable changes), so snapshots stay small and restores rebuild it identically. Editing an obstacle in the entity pane doesn't rebuild it; like the obstacle meshes, that waits for a room editor.
  - `nav/astar.ts`: 8-connected, no corner cutting, octile heuristic, and a binary heap with deterministic tie-breaking (lowest f, then highest g, then lowest cell index). If the goal is unreachable, it returns the path to the closest reached cell.
  - `nav/path.ts`: `findPath(nav, from, to)`. It resolves the goal first: a goal inside an inflated shape is pushed to the closest point outside it (plus a 0.02 m skin), or to the nearest free cell center if that's still blocked. A start inside an obstacle (WASD can walk into walls until 1.3) starts from the nearest free cell. Then it runs A* and string-pulls the result with `segmentClear`, starting from the actual start and goal points.
  - Budget: a worst-case path across the greybox room must take < 1 ms in Node (checked in a test, loosely, so CI noise doesn't flake it). The dmath check's folder list gets `nav/`.
- **Corners:** with no slowdown at corners, steering arcs slightly inside a waypoint (turn radius `v²/accel`, ~0.8 m at the Balanced defaults). That can graze an inflated corner by a few cm before 1.3. That's acceptable now, since 1.3's sliding absorbs it. If it looks bad, the fix is to consume a waypoint only once the next one is in line of sight.
- **Player look** (arena view): a grey-box capsule (radius = `player.radius` at setup, 1.2 m tall, warm orange, its geometry baked so the origin is at its feet) with a small nose box pointing +Z as a child. `ctx.bindMesh` puts it in place of mesh sync's placeholder box, which it disposes, so the capsule is what mesh sync moves, picks and highlights. The player's transform sits on the ground (`y = 0`). It's the camera target and the occlusion focus, like the pawn was.
- **Click marker** (arena view, `render/clickMarker.ts`): a flat ring (torus, cyan-ish, unlit). On an `orders` change it appears at `order.goal`, scales from 0.6 to 1 over 0.12 s and fades out over 0.4 s, on frame time. One reused mesh.
- **Debug draw** (sim side, write-only):
  - `movement`: velocity arrow (yellow), desired-velocity arrow (cyan), facing tick (white)
  - `path`: smoothed waypoints (magenta), goal circle
  - `trail`: `debugDraw.point` at the position every tick with `duration: 2`, so it ages with game time and freezes on pause
  - `navgrid` (from the arena view in `onFrame`): the inflated shape outlines, plus small crosses on the blocked cells along the walkable area's edge (computed once per grid), not on all ~2k blocked cells.
- **Speed graph:** a Tweakpane graph monitor in the **Gameplay** folder showing the player's current speed (0–12 m/s), next to a read-only `speed` number. It reads `__game.world` each frame and shows nothing when there's no player.
- **Movement presets** are commands (group `Movement`, one `define` each, so they get pane buttons and `__game.run`). They set only `accel`, `decel`, `turnAccel` and `turnRate` (speed and radius stay), through `tuning`, so they're recorded like any tunable change. From the sharpest to the heaviest:
  - **Instant**: accel, decel and turnAccel 1000, turnRate 3600
  - **Snappy**: accel 120, decel 175, turnAccel 175, turnRate 720 (the first defaults)
  - **Balanced** (the defaults, added and made the default while playing): accel 60, decel 80, turnAccel 90, turnRate 540
  - **Weighty**: accel 25, decel 30, turnAccel 40, turnRate 360
- **The input test scene goes** (1.1 said it would once 1.2 replaced the pawn): `demo/inputTest.ts`, `demo/inputTest.view.ts`, and the `input-test-basics` fixture. The input overlay already lives in the dev tools, and the stress scene stays (it keeps `demo/ground.view.ts`).
- **Replays:** `arena-walk` keeps its recorded input, and `pnpm replay:update` rewrites its checkpoints for the new controller. A new `arena-paths` fixture covers moba clicks around pillars and through the tight gap, clicking into a wall, hold-to-steer, and `stop`, then WASD starts, reversals and stops.

## Architecture

```
nav/                  (new, Babylon-free)
  shapes.ts           grown circles/rounded boxes: insidePadded, pushOut, segmentDistance/Clear       (tested)
  grid.ts             buildNavGrid, per-world cache                                                     (tested)
  astar.ts            8-connected A*, deterministic heap                                                (tested)
  path.ts             findPath: goal/start resolution, A*, string pulling                               (tested)
ecs/world.ts          + player, mover; − pawn
systems/
  movementStats.ts    movementStats(entity) → the `player` tunables (per-form data at 10.1)
  playerControl.ts    input → desired velocity, move orders, arrival                                    (tested)
  locomotion.ts       accel rule, integration, facing, debug draw                                       (tested)
  pawn.ts             deleted
scenes/arena.ts       systems [playerControl, locomotion]; spawns the player instead of the pawn
scenes/arena.view.ts  player capsule + nose (bindMesh), click marker, navgrid debug draw
render/meshSync.ts    bind() replaces and disposes an entity's placeholder box
render/clickMarker.ts the ring and its pop/fade
debug/                speed graph in Gameplay; movement preset commands
demo/inputTest*       deleted
replay/fixtures/      arena-walk updated, + arena-paths, − input-test-basics
```

Rule 1 holds: `nav/`, `ecs/`, `systems/` and `scenes/arena.ts` import neither Babylon nor Preact, and `nav/` uses only `dmath` for trig and hypot (rule 6).

## Steps

1. `nav/shapes.ts` with tests: inside/outside, closest point outside, segment clearance for circles and rotated boxes, including edge cases like tangent segments and zero-length segments.
2. `nav/grid.ts`, `nav/astar.ts`, `nav/path.ts` with tests:
   - paths avoid every inflated shape (sampled along each segment)
   - the tight gap is passable at radius 0.4 and closed at 0.65 (1.25 m wide, so 0.6 still fits)
   - a goal inside a wall resolves outside it
   - a start inside a wall still gets a path
   - the same inputs always give the same path
   - the performance budget holds
3. Components, `movementStats`, and the `locomotion` system, with tests:
   - reaches top speed in `speed / accel` (± a tick)
   - stops exactly, with no negative drift
   - a reversal passes through zero at `turnAccel`
   - the facing turns at `turnRate` along the shortest arc and holds while stopped
   - `dt` isn't assumed to be one tick
4. `playerControl` with tests: WASD sets the desired velocity and clears orders, `stop` clears orders, a new click bumps `orders` but holding doesn't, repaths happen only on goal cell changes, and arrival lands exactly on the goal without overshoot (checked at several speeds and decels).
5. Arena sim spawns the player; delete the pawn and the input test scene. Update `arena.test.ts` and the scene registries.
6. Arena view: player capsule + nose, click marker, `navgrid` debug draw. Check in the browser that the capsule follows, faces its movement, and that paths route around obstacles.
7. Tuning aids: speed graph, preset commands, and the `trail`/`movement`/`path` categories. Check that the presets record and replay.
8. Replays: `pnpm replay:update` for `arena-walk`, and record `arena-paths`. Then `pnpm check` and `pnpm build`.
9. Verify in agent-browser (acceptance below), and play it by hand. Adjust defaults if something feels off; the real feel pass is 1.7.
10. Docs:
    - AGENTS.md: layout (`nav/`), rule 1's list (+ `nav/`), the arena's player instead of the pawn, the input test gone
    - implementation notes here, tick 1.2, devlog entry `devlog/1.2-player-movement/` (screenshots: path around a pillar, path through the tight gap, the nav grid, the trail for a start/stop and a reversal, the speed graph, the click marker)
    - commit "Player movement (1.2)", push the branch, open a PR, get the checks and Preview green, and report the Preview URL (the user merges)

## Implementation notes

- **Verified in headless Chrome** (agent-browser, real WebGPU) on the dev server:
  - A right-click behind the south-east pillar walked around it and stopped on the click. A click south of the east blocks routed through the 1.25 m gap (the path's corner sat at x 10.875, the middle of the gap), and the click marker popped at the goal.
  - The `navgrid` outlines (rounded boxes, grown circles) sit around every obstacle, with the edge crosses inside them. The `trail` showed straight runs, and a wide turn-around with Weighty.
  - The Gameplay folder's speed graph showed the ramps, and the Movement commands are listed Instant, Snappy, Balanced, Weighty.
- **Played by hand** on a 120 Hz display in Firefox (the devlog video): click-to-move around the arena and through the gaps, with the debug draw on and the presets switched while moving.
- **`arena-paths` was recorded in the browser** (1410 ticks): moba clicks around the pillar, into it, and through the gap; hold-to-steer; `S` mid-walk; the Weighty preset and back; then WASD starts, a reversal, a diagonal and quick taps in `mmo`. It replays without divergence in `pnpm test`, so Chrome and Node agree on every path. The preset changes are in it as eight tunable events.
- **The gap is wider than the plan thought.** At radius 0.6 the player is 1.2 m across, and the gap is 1.25 m, so it still fits. The radius tunable now goes up to 0.8, and the test closes the gap at 0.65.
- **`steering` became `click`.** Storing last tick's command point instead of a flag answers both questions: was the button already held (no new marker), and did the cursor move (repath or not). Holding still on a spot you've reached does nothing.
- **Within a nav cell, holding the button only moves the goal.** The last waypoint is swapped for the new resolved point, with no A*. A new cell paths from scratch. A path corner to corner across the room takes ~0.4 ms in Node (the budget is 1 ms).
- **`bindMesh` replaces the placeholder box.** The player's capsule had to be what mesh sync moves, what picking finds and what the highlight outlines. Binding a mesh to an entity with a transform now disposes the auto-made box, and mesh sync moves the bound mesh instead. A bound mesh is never disposed by mesh sync, including when its entity goes away.
- **Presets only touch the feel.** Setting the whole `player` group would also have undone a speed or radius tweak, so presets set just accel, decel, turnAccel and turnRate.
- **Balanced became the default while playing.** You asked for a preset between Snappy and Weighty, then made it the default. The numbers moved into the tunables' code defaults, Snappy got explicit values, and `arena-walk` (recorded before the `player` group existed, so it runs on the defaults) got new checkpoints. `arena-paths` recorded its own tunable values and didn't need them.
- **Corners are cut a little more with Balanced.** The turn radius at full speed is `v²/accel` ≈ 0.8 m, so a path can graze a grown corner before the steering catches up. The pillar test allows 0.1 m of that until 1.3's collision takes over.
