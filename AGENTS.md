# AGENTS.md

Dark-fantasy druid roguelite for the browser. Babylon.js (WebGPU only) + TypeScript (strict) + Vite.

## Docs (`slopdocs/`)

- Core game design (style & mechanics): [slopdocs/core-game-design.md](slopdocs/core-game-design.md)
- Implementation plan (step order): [slopdocs/implementation-plan.md](slopdocs/implementation-plan.md)
- Misc thoughts (undecided ideas): [slopdocs/misc-thoughts.md](slopdocs/misc-thoughts.md)
- Step plans: [slopdocs/plans/](slopdocs/plans/)
  - **Every implementation step gets its own plan** before any code is written, named `<step>-<slug>.md` (e.g. [`0.1-project-scaffold.md`](slopdocs/plans/0.1-project-scaffold.md)).
  - Write it by interviewing the user (one question at a time) until the plan is solid. Record decisions, defaults picked, steps and acceptance criteria.
  - Link the plan from its step in `implementation-plan.md`, and tick the step there when it's done.

## Devlog (`devlog/`)

- One entry per step in `devlog/<step>-<slug>/index.md`: what we built, key decisions and why, surprises, and screenshots. Template and procedures: [devlog/README.md](devlog/README.md).
- **Finishing a step includes its devlog entry.** Write it from the plan, the commits and the session, take screenshots with agent-browser (look at each one before using it; more for art/atmosphere steps), add it to the index, and commit it with the step.
- Videos are optional and recorded by the user; the pre-commit hook compresses them.

## Commands

Always use **pnpm** (never npm or yarn). Node 24 (`.nvmrc`).

| Command | What it does |
|---|---|
| `pnpm dev` | `cf dev` → Vite dev server on http://localhost:5746 ("STAG"), with the Cloudflare Vite plugin (`public/_headers` applied) |
| `pnpm build` | Typecheck + `cf build` (Vite) to `.cloudflare/output/` (cf's Build Output) |
| `pnpm preview` | Plain `vite build` to `dist/` served in workerd by the Vite plugin (real `_headers`), http://localhost:5746. cf has no local serve of its Build Output yet |
| `pnpm check` | Typecheck + Biome lint/format check + tests. **Must pass before committing.** |
| `pnpm format` | Apply Biome formatting, import sorting and safe fixes |
| `pnpm test` / `pnpm test:watch` | Vitest |
| `pnpm replay:update` | Rewrite the checkpoints of the replay fixtures after an intentional behaviour change (keeps the recorded input) |
| `pnpm models:build` | Rebuild the game-ready models in `public/models/` from the originals in `assets-src/` (gitignored; download links in `scripts/build-models.ts` and CREDITS.md) |
| `pnpm devlog:video` | Compress raw videos in `devlog/` to MP4 + poster and stage them (runs as the husky pre-commit hook; needs ffmpeg) |
| `pnpm exec agent-browser` | Headless browser for devlog screenshots and checks (see `devlog/README.md`) |
| `pnpm cf:preview` / `pnpm cf:deploy` | Build + deploy a Worker Preview for the current branch (`cf previews deploy`) / production (`cf deploy`), with the scoped token from `.env`. Emergencies and agents only; the normal path is a PR |
| `pnpm exec cf …` | The Cloudflare CLI (beta) for everything else Cloudflare: find commands with `cf cli search "<task>"` |

## Repo & deploy

- **Public repo:** [github.com/mvvmm/stag](https://github.com/mvvmm/stag). Production: https://stag.root-mvm.workers.dev (static-assets-only Worker `stag`, config in `cloudflare.config.ts`, built by `@cloudflare/vite-plugin` in `vite.config.ts`, headers in `public/_headers`).
- **We dogfood the `cf` CLI.** Every Cloudflare operation goes through `cf` (pinned exactly, bumped to the latest beta at the start of each step), never Wrangler, the dashboard or raw API calls where cf covers it. Where cf falls short, don't work around it quietly: note it (version, repro, expectation) in the current step's plan under "Friction log" for the cf team. Wrangler is only in the lockfile because the Vite plugin depends on it.
- **Every step is a branch + PR** named `<step>-<slug>`. Nothing is pushed to `main` directly (ruleset: PR required, no force-push). PRs merge with a **merge commit** (the only allowed method), so step commits and devlog links survive. **Agents never merge PRs:** push, get the checks and Preview green, report the Preview URL, and the user merges.
- **Required checks:** `typecheck`, `lint` (`biome ci`: lint + format + import sorting), `test` (incl. replay fixtures), `build` (`.github/workflows/check.yml`), plus `Workers Builds: stag` (the Cloudflare Preview build, so a broken `cloudflare.config.ts` can't reach `main`). Run `pnpm check` before pushing.
- **Cloudflare Workers Builds** deploys, not Actions: every push to a PR branch builds a **Worker Preview**, with `cf previews deploy`, at a stable URL (`<branch>-stag.root-mvm.workers.dev`, follows the latest push), and Cloudflare comments it plus a per-commit URL on the PR. Builds runs it through `scripts/cf-previews-deploy.ts`, which writes the URL where Builds reads it (cf doesn't yet; delete the shim once it does). A merge to `main` deploys production. Playtest the Preview before merging.
- **Credentials:** local `cf` uses an account-owned API token scoped to the `stag` Worker only (role Editor), in `.env` as `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID` (see `.env.example`; cf loads `.env` itself). It can deploy but not change account settings such as Workers Builds (403); those need the user's `cf auth login`, run from outside the repo (cf loads the `.env` token first and it wins over the login). Workers Builds commands are set this way (`cf builds workers update <script tag>`; the tag comes from `cf workers scripts search --name stag`). Workers Builds uses its own user build token until it supports account-owned (per-Worker) tokens.
- **Observability:** Workers Logs + traces are on in `cloudflare.config.ts`. Asset-only requests don't run a script, so they stay empty until the Worker gets code.

public/models/ game-ready glTF models (committed, credited in CREDITS.md)
scripts/      Node dev scripts (run directly with node, e.g. devlog-video.ts, build-models.ts)
src/

  systems/    pure simulation systems: (world, dt) => void. Player movement is playerControl (input → desired velocity, paths) then locomotion (any `mover`: integrates through collision's moveAndSlide unless `noclip`); movement numbers, the movement radius included, come only from movementStats(entity); the facing follows where the body actually moved (or where it wants to go when blocked), and a ~180° reversal swings back through the side it came from (`mover.turnSide`). cheats.ts holds the sim cheats (`simCommands`)
  render/     Babylon scene setup, entity↔mesh sync, views; the game camera (scene.ts places it from the `camera` tunables; cameraRig.ts, Babylon-free and tested, is the view-only follow: cursor look-ahead from the cursor's screen position, eased offset, clamp to the scene's bounds); the atmosphere (atmosphere.ts: one rig built by the shell and shared by every scene: moon + fitted shadow map, ambient fill, the player's warm light, exp2 + height fog, the post stack incl. SSAO and curves grading, the `overlay` scene drawn after post for markers and debug draw, the atmosphere-off/value-view switches; its numbers are the `light`/`shadow`/`fog`/`post`/`grade` tunables; fogMath.ts, Babylon-free and tested: analytic height fog, pulse, shadow frustum fit; heightFog.ts and floorMaterial.ts are WGSL material plugins; materials.ts makes the grey-box PBR materials); models (models.ts: glTF files preloaded once at boot into asset containers, instantiated per scene); the player's body (tiger.ts: the tiger model with its gait clips (idle/walk/trot/run) blended by the player's speed and sampled on `ctx.viewTime()`, plus procedural breathing, lean, tilt, a living tail (side-to-side and up-and-down spring chains driven by repeatable noise of the view time, occasional bigger swings, the stride and turns) and head look, and (1.7) a spine that bends through turns, a push-off on starts, stops that finish the step and settle, shuffle steps for short moves and a slowed gallop at cruise, played as a bound (the run's left/right legs pulled together in time) with the body's bounce, rock and back arch (an upside-down V as the legs gather) worked out from the run's own foot contacts at load; its numbers are the `tiger`/`anim` tunables; locomotionAnim.ts, Babylon-free and tested: gait blend and the gait driver (start, shuffle, stop), springs and the tail's spring chain, the spine bend, bank and look angles; rimMaterial.ts is a WGSL fresnel rim plugin (`rim` tunables); bodyView.ts is the hitboxes switch)
  input/      action bindings/presets, input state → per-tick InputFrame (dom.ts is the only DOM adapter)
  ui/         Preact HTML overlay (components, signals, CSS modules, styles/tokens.css); PauseMenu.tsx is the Esc menu (resume, control scheme)
  data/       data-driven definitions (Babylon-free): rooms/ (hand-built room layouts: obstacles as circles/rotated boxes; greybox = the combat room, gym = the collision test bench), later abilities, augments, enemies
  debug/      dev tools (lazy, DEBUG only): commands, pane, stats/profiler, debug-draw renderer, Inspector, replay session (debug/replay/), stand-in threats (standIns.ts)
  replay/     record & replay core, Babylon-free: file format, checksums, recorder, player, headless runner; fixtures/ are regression tests
  scenes/     SceneSim (sim.ts, Babylon-free) + SceneDef/SceneContext (scene.ts), registries (sims.ts headless, index.ts full), room scenes (arena.ts: `roomSim(id, label, room)` → `arena` (greybox, the default scene) and `gym`; arena.view.ts: the shared room view with player body, click marker, occluder fading)
  nav/        pathfinding (Babylon-free): obstacles grown by a radius (shapes.ts), exact tangent graph over the grown shapes cached per world (graph.ts: circles = pillars and rounded box corners, edges = clear tangents + free arcs), generic deterministic A* (astar.ts), findPath (path.ts: start/goal tangents, arcs walked as a polygon 1 mm outside, closest reachable point when blocked). ## Architecture rules

1. **Simulation is separate from rendering.** Code in `ecs/`, `systems/`, `replay/`, `input/` (except `input/dom.ts`), `data/`, `nav/`, `collision/`, scene sim halves (`scenes/sim*.ts`, `scenes/arena.ts`, `demo/*.ts` except `*.view.ts`), plus pure `core/` helpers, must never import `@babylonjs/*` or `preact`. That keeps it unit-testable and replayable in Node.
2. **Babylon mirrors the ECS.** `render/` creates and disposes meshes through miniplex query `onEntityAdded` / `onEntityRemoved` events, and copies state from components each frame.
3. **The UI reads signals.** The game writes `@preact/signals` at low frequency, and Preact components read them. The UI never reaches into the ECS directly. The `#ui` overlay has `pointer-events: none`, so interactive elements must opt back in.
4. **Content is data.** Abilities, augments, enemies and rooms are defined as data in `data/`, not as bespoke code paths.
5. **Fixed timestep.** The simulation advances in fixed ticks (`TICK_HZ` in `core/constants.ts`, currently 60). Systems get `dt` in seconds and must never assume a tick count. Rendering interpolates between `prevTransform` and `transform`; call `snapTransform()` after teleports/spawns.
6. **Determinism.** Simulation code (`ecs/`, `systems/`, `nav/`, `collision/`, scene sims, pure `core/`) uses only the `dt` it's given, takes randomness only from the seeded `Rng` passed in (never `Math.random`), never reads wall-clock time (`Date.now`, `performance.now`), and uses `dmath` (`core/dmath.ts`: `sin`, `cos`, `atan`, `atan2`, `hypot`) instead of `Math.sin/cos/atan2/hypot/pow/exp/…` or `**`, because those differ in the last bit between engines (Chrome and Node really disagree) and replays drift. `+ - * /` and `Math.sqrt/floor/round/abs/min/max` are exact and fine. A test (`core/dmath.test.ts`) fails on forbidden calls in sim code.
7. **Input is a per-tick snapshot.** Systems are `(world, dt, rng, input: InputFrame) => void` and read input only from that frame (actions by role: `primary`, `ability1`, …, never raw keys; world-space `move`, `moveCommand`, `aim`, quantized to a 1/1024 grid so replays feed back identical values). A press is in `pressed` for exactly one tick. Bindings are data in `input/bindings.ts` (`mmo` and `moba` presets). Shell-level actions (`pause` on <kbd>Esc</kbd>, which opens the pause menu, `switchControls` on <kbd>M</kbd>, moba's `centerCamera` on <kbd>Space</kbd>) use `sampleFrame()` so they work while paused; they're game controls, not dev keys. Both schemes are a player setting, `mmo` (WASD) by default; the pane's pause doesn't open the menu. In the moba scheme a canvas click locks the pointer (`input/dom.ts`: a virtual cursor from mouse movement, drawn by `ui/softwareCursor.ts`; Esc releases it) and the camera is free: it pans at the screen edges (`camera.edgePan*`) and Space re-centers it (held: follows). WASD keeps the follow camera with cursor look-ahead.
8. **Tune through tunables.** Numbers worth tweaking live in `defineTunables("group", { key: { value, min, max, step } })` (`core/tuning.ts`; also booleans, selects `{ value, options }` and sRGB colors `{ value: "#rrggbb", color: true }`), which returns a live object: read it every time, never cache a value. They show up in the debug pane. Code defaults stay the source of truth: "Copy changes" in the pane gives a `group.key: old → new` snippet to paste back.
9. **Debug draw is write-only.** Any code, systems included, may call `debugDraw.line/arrow/circle/box/point/path/text` (`core/debugDraw.ts`) with a `category`. Never read from it or branch on it in the simulation. It's a no-op in player builds; debug builds always record it, and each category is toggled in the pane's View folder (new ones start hidden).
10. **Scenes are resettable, and split into sim and view.** A scene's sim half is a `SceneSim` (`scenes/sim.ts`: `id`, `label`, its `systems`, `spawn(world, rng)`), listed in `scenes/sims.ts`; the full `SceneDef` adds a view `setup(ctx)` (`scenes/scene.ts`), listed in `scenes/index.ts`. Every `shell.load(def, seed)` / `shell.restart()` tears the old scene down and builds a fresh world, RNG, simulation and mesh sync at tick 0, runs `spawn`, then `setup`. Setup is view-only (a headless replay never runs it): it reads the world but doesn't change it or use the RNG, registers everything through `ctx` (`own`, `onTick`, `onFrame`, `onBeforeRender`, `onTunableChange`, `onDispose`; `bindMesh` links a mesh it built itself, e.g. a static obstacle or the player's body, to its entity for picking, replacing mesh sync's placeholder box for an entity with a transform; `setCameraTarget` gives the game camera something to follow, `setCameraBounds` a ground rect its look-at point stays in; `setShadowCasters` lists the meshes that cast moon shadows (the frustum is fit to them, and receivers set `receiveShadows`), `setLightTarget` what the player's warm light hangs over, and `overlay` is the scene for markers that must skip lighting, fog and post) and keeps no state between runs. `viewTime()` is the simulation time the view shows (it stops while paused, follows frame steps, the time scale and replay seeks): view animation that should match the sim runs on it. Scenes build their own ground. Never hold on to `shell.world` or `shell.rng`; read them when needed (or listen to `shell.onLoad`).
11. **Only systems and recorded events change the sim.** Every run is recorded (seed, tick-0 tunables, per-tick input, out-of-band events) for replay. Anything else that changes simulation state must be one of the recorded kinds: a tunable change, an entity-pane edit (`tools.editField`), or a debug command defined with `sim: true`. Sim commands are Babylon-free entries in `systems/cheats.ts` (`simCommands`, `(world) => void`), so headless replays run them too; the pane defines one command per entry (`debug/cheats.ts`). Scene `onTick`/`onFrame`/`onBeforeRender` listeners are view-only. Components are plain data (numbers, strings, booleans, null, arrays, plain objects; no class instances, functions or references to other entities' objects), so a snapshot can restore the world exactly.
12. **Dev tools are gated and pane-driven.** `src/debug/` loads only when `DEBUG` (`pnpm dev`, or `?debug` in a production build) as a lazy chunk, so players never download it. There are **no dev keybinds**: the keyboard always belongs to the game, and every dev tool is controlled from the debug pane. The only dev key is <kbd>`</kbd>, which hides/shows the pane. New debug actions (cheats) are commands (`debug/commands.ts`, one `define` each), which get a pane button and `__game.run(id)`.

## Conventions

- TypeScript strict with `noUncheckedIndexedAccess`; use the `@/` import alias for `src/`.
- Biome handles formatting and linting (no ESLint or Prettier).
- Tests cover pure logic only (systems, math, cooldowns, modifiers, RNG) and sit next to the code as `*.test.ts`, running in the Node environment. Keep Babylon out of tests; check rendering and feel by playing.
- Styling: CSS Modules (`*.module.css`) plus design tokens as CSS custom properties in `src/ui/styles/tokens.css`.
- Babylon: import from the `@babylonjs/core` root for now (deep imports may come in the 9.6 performance pass).
- **The repo is public.** Never commit secrets: credentials go in a gitignored `.env` (names documented in `.env.example`). Third-party assets get a row in [CREDITS.md](CREDITS.md) (source, license, credit) before use. Only redistributable ones (CC0, CC-BY, …) are committed. Store-EULA assets that allow shipping but not redistribution never go in the repo (they go to R2).
- Rendering is **WebGPU only** (`WebGPUEngine`); custom shaders should be WGSL. Dev-only `?unsupported=device|webgpu|error` previews the Unsupported screen.

## Dev tools

- The debug pane (Tweakpane, top right) is always there in debug builds, and <kbd>`</kbd> hides/shows it. While the Babylon Inspector is open the pane steps aside; a "Close Inspector" button over the game view (or <kbd>`</kbd>) closes it and brings the pane back. It covers the scene (switcher, seed, restart, new seed), replay (save, save as test, load, checked-in tests; while playing: timeline, go to tick, step back/step, take over, exit, sync status), time (pause, frame step, tick, time scale, interpolation), gameplay (control preset, cheats such as noclip, the player speed graph), view (everything painted on screen: stats mode, input overlay in every scene, wireframe, atmosphere (off = flat grey-box lighting, no fog, shadows or post), value view (greyscale), stand-in threats (view-only telegraphs and an enemy silhouette in room scenes), hitboxes (no models): the player's grey-box movement capsule instead of the tiger (the `footprint` debug category draws the movement circle and the body's hit pill), free camera, one toggle per debug-draw category, which start hidden, and the Inspector at the bottom), the entity picker ("pick in world" borrows the mouse and outlines what's under the cursor; the selection gets its own pane with its live, editable components), tunables and command buttons (including the Movement presets and the Gallop presets: Natural, and Pouncy, the default). Using a pane control hands the keyboard back to the game (text fields keep it until Enter).
- `?scene=<id>` and `?seed=<uint32>` pick the startup scene and seed in debug builds only (read once, never written; players never deal with URLs). Without them, a reload returns to the last scene with a fresh seed.
- The Babylon Inspector is only in `pnpm dev` builds (bundling it into production pulls ~380 KB gzipped of core into the player chunks).
- For automated checks (agent-browser `eval`), use `window.__game`: `world` (the current scene's), `loop`, `input`, `scenes.load("stress", 42)`/`scenes.restart()`/`scenes.current()`, `seed`, `select(id)`/`selected`, `tunables.get/set/reset/changes`, `run("loop.step")`, `replay.recording()/play(file|bytes|url)/seek(tick)/stepBack()/takeOver()/exit()/stop()/newRecording()/save()/status`, `tools.setStats("full")` etc. (typed in `src/env.d.ts`). Debug settings persist in localStorage under `stag.debug`.
- **Record & replay:** every load starts a recording (capped at 60 min). "Stop recording" freezes it (saving keeps it); "New recording" forgets it and records from right now by snapshotting the world, RNG and tunables into the file. "Save replay" downloads `<scene>-<seed>-<time>.replay.json.gz`; "Load replay…" or dropping a file on the page plays it back through the in-place reset, checking a checkpoint every second (playback pauses at the first divergence and names the components). A replay's tunables are applied during playback and yours come back on exit. In `pnpm dev`, "Save as test…" writes to `src/replay/fixtures/`, where every file is a Vitest regression test; after an intentional behaviour change run `pnpm replay:update`. Replays are only valid for the code they were recorded on.
